指标口径赛道扫描

问题：全球云厂商数据平台与专业数据工具里，"自动化展示指标口径"上线了吗？ 覆盖国际云厂商 5 家、国内厂商与指标平台 13 家、数据目录/治理工具 11 家、语义层与 BI 10 家，共 39 个产品， 以官方文档 / 发布说明为准（营销稿单独标注）。

结论：没有任何一家达到 L4——"对存量多层 SQL 自动做字段级血缘 + LLM 逐层解读 → 互验合成业务/技术双口径 → 在看板指标卡上面向业务读者原生透出（带置信分级与证据溯源）"这条完整链路，截至检索日无人上线。 你之前的调研结论仍然成立。但窗口正在收窄：2026 年 Snowflake、Atlan、Aloudata 都在"自动提取存量指标语义"上发了真动作，只是没人走到消费端。
§1

判定框架与竞争格局

为避免"有 AI 功能"和"能透出口径"混为一谈，全部产品按两个维度定位：自动化程度 （L1 人工登记 → L2 预定义语义层 → L3 AI 辅助元数据 → L4 存量口径自动合成）与产出落点 （开发者工具 → 治理/目录侧 → 消费端看板）。市面的分布高度一致：L2 在消费端有出口，L3 全部停在治理/开发者侧，右上角是空的。

§3

为什么没人上线 L4——五个原因

  1. 商业动机错位（最根本）。云厂商和指标平台卖的是"正向治理"：先注册定义、生产消费都走单一出口，客户为"收敛"付费。逆向从存量提取口径，等于承认"不先买我的指标平台也能把口径说清楚"——这与自家 L2 产品线左右互搏。所以巨头的 AI 全部长在"帮你更快建语义层"（AtScale 一键建模、dbt Copilot、数势语义工厂），而不是"替你解释存量"。
  2. 责任与准确率风险。口径展示错了比不展示更糟：业务按错口径做决策，责任落在展示方。看遍 39 家，所有 AI 元数据功能一律是"草稿 + 人审 + AI 标记"形态（DataHub 的 sparkle 图标、Select Star 的 Draft 标签、Atlan 的人审认证），没有一家敢把 AI 生成的内容直接放到业务侧看板。缺一套"机器可验证"的置信机制，就不敢过这条线——这正是双通道互验 + 证据绑定要解决的问题。
  3. 解析覆盖率是工程深坑。真实环境字段级血缘本身就是行业老大难（Aloudata 拿"Oracle/DB2 解析准确率 90%"当核心卖点），跨引擎方言、存储过程、脚本拼 SQL、Flink 代码都会断链。多层端到端语义等效还原比血缘更难一层。云厂商只看得到自己引擎内的那一段，谁都没有跨栈全量视角。
  4. 买单人分裂。口径之痛长在消费端（业务、分析师），预算在生产端（数据平台团队），而生产端的 KPI 是"建好语义层"不是"解释存量"。没有天然采购路径，产品化动力不足。
  5. 技术窗口 2024 年后才打开。可靠的 LLM 逐层 SQL 解读需要长上下文 + 强 SQL 理解 + 可接受的成本，这是近两年的事。巨头先摘的是低风险果子（表/列描述），指标级端到端是下一站——Snowflake Autopilot（2026-02 GA）、Cortex Sense（2026-06 私预）、Atlan Context Agents（2026-06）说明他们正在路上，只是当前目的地是"喂 AI agent / 建语义层"，不是"给人看"。

趋势判断：空位是真的，但不是永久的。三个信号——① Snowflake 已做"查询历史→指标建议 + 用法漂移监控"；② Atlan 宣布"推断 metrics"；③ Fabric metric sets 之死说明纯人工注册形态在退潮。合理预期 12–24 个月内会有巨头把"自动提取"推到消费端。先发优势要靠互验可信度（他们都没有）和消费端体验（他们都不在）来守。

§4

MetricLens 距真实线上应用的差距

按"技术墙 → 信任墙 → 工程底座"三层排序；每条都对照当前实现（dbt + DuckDB、15 指标、单机）如实评估。

技术墙：解析覆盖面（最硬的一堵）

  • 方言与形态。现在的 100% 血缘成立于"每个模型是一个干净 SELECT、单一 DuckDB 方言"。真实生产是 Hive/Spark/Flink/ClickHouse 混布 + 自定义 UDF + 存储过程 + Python 脚本拼 SQL + Flink DataStream（根本没有 SQL 文本）。血缘一断链，通道一为空，互验失去锚点，整卡降级——解析成功率直接决定产品可用面。
  • BI 最后一公里。我们直读 APP 表；真实看板经过 BI 私有语义层（数据集/计算字段），"看板字段 → SQL"的映射要逐家 BI 适配（Tableau/QuickBI/自研）。euno 和 Select Star 恰好做的是这一段，是潜在的互补对象。
  • 规模与增量。15 指标全量重算分钟级；真实是数千看板 × 数万指标 × 日均数百次变更，需要增量血缘（只重算受影响子图）、变更触发定点刷新、LLM 成本预算控制。内容寻址缓存方向对，增量图计算还没有。

信任墙：口径的权威性与责任

  • 认证工作流缺失。自动提取的口径"无主"。真实落地形态几乎必然是"AI 起草 → 指标 owner 确认 → 盖章发布"，卡片要区分"AI 合成（高置信）"与"owner 已认证"两种状态，配争议与修订流程。这不是妥协——调研显示这是全行业铁律（无一家跳过人审），我们的置信分级恰好是这套工作流的天然底座。
  • 评测自证问题。14/14、100% 全部出在自造数仓 + 自造陷阱上。上线前需要：客户环境抽样人工标注 golden set、按库回归、线上"口径不对"反馈闭环。没有跨库 benchmark，准确率宣称不可信。
  • LLM 私有化。SQL 含表结构与业务逻辑，多数数据团队不允许出内网——需要私有化模型部署或脱敏层；数万指标规模下 PROMPT_VER 升级引发的全量重跑是真金白银。

工程底座：从演示到服务

  • 权限：技术口径会暴露底层表结构与过滤逻辑，需对齐行/列级权限（谁能看哪层口径）；多租户、审计、SSO。
  • 高可用：单机 DuckDB + 文件指针 → 元数据库 + 对象存储 + 服务化部署。
  • 漂移快照当前只覆盖 15 个看板指标，全列漂移在真实规模是增量图计算问题。
  • 生态位：真实买家已有目录/元数据平台（DataHub/Dataphin/Atlan），MetricLens 更现实的形态是"口径引擎/插件"接入既有体系，而非再造一个平台。

落地形态建议（按可行性排序）

  1. 存量口径考古工具——服务"要上指标平台但存量没人说得清"的团队，做一次性口径盘点与迁移 bootstrap。与 L2 指标平台是互补而非竞争（帮它们冷启动），也避开与巨头正面相撞。
  2. BI 口径插件——在既有看板上加"口径 ⓘ"层，不替换任何现有系统；消费端体验是全场唯一空位，也是我们已验证的部分。
  3. 治理巡检服务——漂移检测 + 重复建设扫描作为持续订阅价值（Snowflake 已验证"用法漂移监控"是刚需方向）。

要守住的差异化硬点：双通道互验 + 逐条证据绑定（全场 AI 功能都没有 verification story）、消费端原生透出（全场空位）、漂移与指纹治理（仅 Snowflake/euno 有雏形）。
