§2

线上代码变更 → 口径更新方案

模型 SQL 一旦变更，两条发布轨道保证"线上任何时刻都是完整一致的状态"：数据轨全自动、全验收通过才原子切换； 口径轨涉及付费 LLM 调用，由漂移信号提示人工触发，整批成功才切指针。两轨各自失败都不影响线上。

失败与一致性语义

  • 数据轨失败：rebuild 非零退出，*_build 副本残留供排查；正式 duckdb 与 graph.json 保持旧版本且二者始终配套。
  • 口径轨失败：任一卡合成失败则整批不发布、active_run 指针不动（已真实演练：DeepSeek 截断导致 1/15 失败，线上零感知）。--only 单卡重跑会从当前 active 批次复制其余 14 张，保证每个发布批次都是完整集合。
  • 缓存使更新便宜：LLM 调用按 PROMPT_VER|model|system|user 内容寻址缓存——只改一个模型的 SQL 时，只有途经该模型的 hop 与相关归并是真实付费调用，其余全部命中缓存。

何时必须刷新口径卡——漂移检测给出触发规则：source / condition / semantic 类 high 事件意味着口径实质变化，看板角标立即出现（角标来自漂移事件，不依赖口径卡刷新）， 应尽快跑 caliber_refresh.sh 让口径卡追上；medium（表达式文本变化）可能只是无害重构，可批量攒到下次刷新。 需要硬门禁时用 python -m governance.drift --strict：high 事件直接非零退出，可挂进 CI 阻断发布。

§3

口径合成：双通道互验与受控生成

口径卡的可信度来自一个结构性约定：LLM 永远不单独作为事实来源。确定性血缘（通道一）与 LLM 逐跳解析（通道二）彼此独立取证，机器互验后才允许进入卡片；业务口径的每一条款必须绑定确定性证据编号。

三道反幻觉闸门

  1. 原文引用机器校验——通道二每条过滤必须附逐字符 SQL 原文引用，归一化后在原文中找不到（含空引用）即 quote_fail，直接惩罚置信。
  2. 归并前五分类过滤——每条 LLM 过滤经同一条件归一化管道（化简 + 字面量换边 + 去别名 + 指纹）与通道一比对：matched（本指标真实口径）/ pure_key（关联键）/ out_of_scope（同模型其他列的真实条件，不惩罚也不进卡）/ unparsed / suspect（任何模型条件集中都找不到，重罚）。只有 matched 进入技术口径归并。
  3. 证据 ID 绑定——业务条款必须引用 E/S/X/Q 编号证据（全部来自确定性来源），basis 需与所引证据做 token 命中校验；任一未绑定条款 → 该卡不得 high。

置信与发布规则

置信条件（全部满足）发布行为
high 源字段零漏零多 · 条件覆盖 ≥ 99.9% · 零 quote_fail · 零 suspect · 全部条款绑定证据 上看板，完整展示
medium 零漏源 · 多报 ≤ 1（条件列豁免后）· 覆盖 ≥ 80% · suspect ≤ 1；或 high 因未绑证据条款被封顶 上看板，标注表述差异
low 其余情况 进人工审核队列；API 仅返回状态占位，技术/业务内容不外泄

当前 active 批次：15/15 全部 high，互验零可疑、零未绑定条款，陷阱揭示 14/14（验收线 ≥12）。

§4

指标治理逻辑

治理回答两个问题：存量重复——哪些指标是同一口径的多处物化（该收敛）； 增量漂移——哪次变更悄悄改了口径（该告示）。两者都建立在血缘引擎的确定性产物上，LLM 只在指纹无法区分语义时出场仲裁。

重复建设：指纹分档 + 语义仲裁

  • 指纹定义：md5(sorted(ODS 源字段集) + sorted(非纯键条件指纹集))，条件指纹来自与互验同一条归一化管道——同一套等价判定贯穿口径与治理。
  • 卡片注入：A 档对按「同模型 + 同基名」匹配指标链路（refund_amt_14d 与兄弟列 refund_amt_total 视为同主题），命中即写入卡片 governance.duplicates，口径弹层展示"同源同构"提示。
  • 当前结论：A 档 16 对重复物化（GMV/支付额/支付人数等跨 app/dm 多处物化，建议收敛到血缘最上游出口）；B 档 10 对全部仲裁为同源不同义（合理，不收敛）。T8 靶向对（交易域 refund_amt ↔ 售后域 refund_amt_total）由扫描自动发现并进入 refund_amt_14d 卡的治理提示。

口径漂移：快照对比与严重度

每次重建后对 15 个指标做规范化快照（只含确定性事实），与最近快照逐项比对，事件写入 append-only 日志：

变更类型严重度依据
源字段增删 source_added/removedhigh取数来源变了，口径实质变化
过滤条件增删 condition_added/removedhigh行集定义变了（按归一化指纹比对，改写不误报）
语义点增删 semantic_added/removedhigh窗口去重 / CASE WHEN / COALESCE / 统计日——14 道陷阱有一半藏在这些结构里，14→15 天窗口就落在这类
表达式文本变化 expr_changedmedium可能只是无害重构，归一化文本无法区分语义等价
指标上线/下线 metric_added/removedinfo集合变化，非口径变化

已跑通的真实演练：把 14 天退款窗口临时改为 15 天 → dbt compile → 血缘图重建 → 检测精准命中且仅命中 refund_rate_14d 与 refund_amt_14d（语义点替换 high ×2 + 表达式变更 medium ×1，各两指标）；还原后检出对称回归事件。 数据库全程未动——漂移检测只依赖编译产物与血缘图，比重跑数据便宜几个数量级。12 条真实事件现在就在看板治理台与两张卡的变更历史里。
